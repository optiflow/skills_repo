# Back-Briefing Notes

Use this reference when you need the rationale or source-backed guardrails for the `back-brief` workflow.

## Source Basis

- Fivecoat Consulting Group describes a back brief as a receiver summarizing the task, plan, or instructions back to the leader in their own words so the leader can check whether the message was received correctly: https://www.thefivecoatconsultinggroup.com/the-coronavirus-crisis/backbrief
- Workz describes backbriefing as a method for turning strategic intent into local action through a brief, team translation, briefing back, and feedback/alignment: https://workzchange.com/backbriefing-for-empowerment/

## Core Model

1. The requester gives intent, task, or direction.
2. The receiver says the task back in their own words.
3. The requester checks understanding and corrects gaps.
4. The receiver translates intent into concrete action.
5. The requester gives feedback to align priorities and remove confusion.

## Agent Use

For AI agents, the receiver is the agent and the requester is the user.

A useful agent back-brief should cover:

- Goal: what the user is asking for.
- Done when: what success means.
- Constraints: files, scope, non-goals, style, risk, and safety limits.
- Plan: the shortest clear path to execution.
- Open points: assumptions or questions that could change the work.

## Guardrails

- Use back-briefing to align and empower, not to micromanage the user.
- Do not rush the dialogue when the task is risky, broad, expensive, or unclear.
- Ask only questions that could change the task, plan, or success checks.
- For trivial one-step read-only requests, avoid adding process unless the user asks for it.
- If corrected, restate the corrected task before material action when the correction changes scope, risk, or output.
